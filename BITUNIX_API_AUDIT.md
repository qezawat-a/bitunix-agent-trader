# Bitunix Futures API Contract Audit

**Audit date:** 2026-09-30
**Source audited:** `bitunix-agent-trader-balance-fixed.zip`, compared with the repository's `main` baseline at `25b87b3`
**Scope:** Every REST endpoint wrapper implemented in `src/bitunix/client.js`, its actual call sites, shared REST/WebSocket signing helpers, and the market/account/order/position response handling those call sites use. This audit does not add strategies or new exchange capabilities.

## Result

The source tree and `main` baseline matched before changes. The audit verified **22 unique implemented REST routes**. It found and fixed incorrect leverage-mode and position-TP/SL paths, an omitted required query parameter, an unsupported default depth tier, REST signature canonicalization that changed spaces inside string values, a defaulted order request missing documented LIMIT fields, an unexposed close-position identifier, acceptance of responses without the documented application code, a local/API margin-mode spelling mismatch, and K-line volume normalization that ignored Bitunix's `baseVol` field.

All checks used documentation examples and mocked `fetch` responses. **No real Bitunix request, order, trading toggle, or exchange setting change was made.** `LIVE_TRADING=0` and `ARM_TRADING=0` remain the example defaults. Only `place_order` is exposed by the agent's current tool list; other write methods below are client wrappers and were tested with a fake fetch in a child process that could not access the network.

## Shared authentication, signatures, and responses

| Status | Area | Result |
|---|---|---|
| Mismatch — fixed | REST signature canonicalization | Official [signature docs](https://www.bitunix.com/api-docs/futures/common/sign.html) require query keys sorted in ascending ASCII order, concatenated as key+value; body JSON compacted; then `SHA256(nonce + timestamp + api-key + queryParams + body)`, followed by `SHA256(digest + secretKey)`. The request uses a 32-character random nonce and millisecond timestamp. The prior code removed whitespace globally from serialized JSON, which changed string values containing spaces; it now signs the exact compact `JSON.stringify` body sent on the wire. Mock tests independently recompute the signature. |
| Verified | REST authentication headers | Public calls do not attach API credentials/signature. Private calls use `api-key`, `nonce`, millisecond `timestamp`, and `sign`; `Content-Type: application/json` and `language: en-US` match official request examples. GET query params and POST JSON bodies are sent in their documented locations. |
| Verified | WebSocket signing helper | The unused helper's login signature uses seconds and the documented double-SHA256 formula. There is **no WebSocket connection, login, channel subscription, or event handler implemented** in this project; channel APIs are therefore not treated as working features. |
| Mismatch — fixed | Application-code parsing | Official responses use an envelope with `code`; code `0` is success and errors commonly arrive with HTTP 200. The client already rejected nonzero numeric/string codes but previously accepted a missing/invalid code; it now fails closed on malformed envelopes. Partial cancellation failures remain visible in returned data. |
| Verified with source-doc discrepancy | Error code handling | The [current error-code page](https://www.bitunix.com/api-docs/futures/ErrorCode/error_code.html) lists `0` as success and application errors with HTTP 200. The position-mode page's sample uses code `200014` for existing positions/orders, while the error-code catalogue describes the analogous condition as `20009`; no behavior is inferred from that conflict—the client rejects either because both are nonzero. |
| Verified | Current changelog | The [official changelog](https://www.bitunix.com/api-docs/futures/log/change_log.html), fetched on the audit date, only returns a 2026-06-15 WebSocket connection-limit update: maximum five messages/second, including ping/pong and subscribe/unsubscribe JSON. The project has no WebSocket client, so this required no endpoint-code change. |

### Timeframe documentation note

The [K-line page](https://www.bitunix.com/api-docs/futures/market/get_kline.html) describes intervals “such as” `1m`, `5m`, `15m`, `30m`, `1h`, `2h`, `4h`, `6h`, `8h`, `12h`, `1d`, `3d`, `1w`, and `1M`; it does not declare a closed enum. The project also accepts `3m`. Because the page's wording is illustrative rather than a closed allowlist, `3m` cannot be proven invalid from that page, but it is not explicitly listed either. Existing timeframe parsing/default behavior was preserved rather than changing it based on an unsupported inference.

## Credential and Git-history risk (important)

The GitHub repository is **public**. A credential-pattern review of the existing history found a previously committed `.env` in commit `6b1d1573` with nonempty values under `OPENAI_COMPATIBLE_KEY`, `BITUNIX_API_KEY`, `BITUNIX_API_SECRET`, and `TELEGRAM_BOT_TOKEN`. **No values are included here or were used.** Treat those credentials as compromised and revoke/rotate them at their respective providers (prioritize the Bitunix API key/secret and Telegram bot token). The old raw credential pasted in chat was not used.

The current branch tree contains no `.env`; a `.gitignore` now excludes environment files, key files, and `node_modules`. The current tree also removes 448 tracked `node_modules` files. **This does not purge prior Git history:** the historical `.env` and dependency blobs remain reachable in old commits because no history rewrite was performed. Removing a secret from current files or making this new commit cannot revoke it or erase old public copies. Consider a separately planned history rewrite only after credential rotation and coordination with any existing clones/forks.
